## 01. 一句话定位

*作品是什么*

**知时智农** 是一个 **农事时机问答智能体**：面向华北平原冬小麦 / 夏玉米种植户的农事时机决策智能体。

把天气预报，翻译成此刻能不能下地。站在地头，手机在手：预报只说「多云 3 级风」，可你真正要知道的是——今天几点风最小、雨前够不够打完一遍药。

把课堂里学到的 AI 用到田埂上，让一次打药、一次冬灌，有一个能说清依据的时间点。

> 主题不靠标语：把「青年用 AI 解决真实问题」落到「地头、一次打药、一个能说清依据的时间点」这个具体场景里。

## 02. 背景与真问题

*为什么要做*

天气预报回答的是「明天多云、3 级风」，农户要做的是「今天下午三点能不能下地打药」。中间隔着一道翻译：风速按小时怎么变、雨前有没有连续够长的窗口、气温会不会影响药效。

这道翻译通常靠经验。经验可靠的老师傅能判断，但刚接手地块的人、返乡帮忙的学生、临时雇工，往往只能看个大概：要么错过窗口，要么药打完就下雨。

更麻烦的是，通用大模型可以直接编一段「建议明天上午打药」，但没人知道它依据哪个风速、哪个阈值，数字错了也没人拦得住。所以问题不是「有没有 AI」，而是**「AI 给出的农事结论能不能被核对」**。

> 问题来源：项目成员在华北平原农田场景中的观察，以及对公开天气预报产品、公开农技文件与地方标准的对照。本说明不引用任何未经核实的用户访谈数、满意度或实验数据。

## 03. 服务对象与使用场景

*谁用、在哪用*

**主要用户**：华北平原以冬小麦 / 夏玉米为主的小规模种植户、家庭农场；以及农业院校学生在田间实习、返乡实践时随用随问的场景。

**典型场景**：站在地头、手里只有一部手机：想知道今天能不能打药、要不要浇水、能不能晾晒，而不是自己读七张天气表格。

- 早上出门前：看今天有没有窗口、几点到几点，顺手看依据；
- 雨前抢活：比较「今天下午」和「后天上午」哪个更稳；
- 拿不准时：问「为什么这么判」，把阈值和数据源翻出来自己核一遍；
- 问到不会的：智能体明确拒答，并给出该找谁（农技员 / 植保站 / 农药标签）。

**能带来的改变**：把「读七张天气表格 + 凭经验猜」压缩成「一个时间区间 + 一条可核对的依据」；阈值按属地公开文件自动套用，市级更严时优先，不要求用户自己查文件。

## 04. 知识范围与资料来源

*能答什么、依据在哪*

知识范围被明确划定，不是「什么都能聊」：
能回答**

- 未来七天，哪一天、几点到几点适合打药，以及为什么
- 这几天要不要浇水，雨前浇了会不会白浇
- 哪几天适合晾晒 / 入库
- 今天与未来七天的天气、风速、降水与气温
- 判定用了哪些阈值、数据从哪来、结论有多可靠
- 你所在市按哪份农技文件、风速 / 气温 / 时段的具体限值是多少
- 当前节气与对应的农事提醒
不回答**

- 病虫害识别、药名与配比推荐（需要图像识别与植保资质）
- 测土配方施肥、产量预测、农产品价格与补贴政策
- 真实苗情 / 长势结论（遥感尚未接入）
- 任何替代农药标签、当地农技部门意见的最终决策

| 来源 | 用途 | 性质 / 备注 |
| --- | --- | --- |
| 和风天气 | 主预报：逐小时风速 / 气温 / 降水、7 天日值 | 公开气象服务；页面每次打开时实时请求 |

> 知识库不是「把百科塞进提示词」，而是「实时数据 + 可解释规则 + 明确的拒答边界」。任何回答都能追到具体阈值和数据源。

## 05. 技术方案与实现

*怎么做的*

**技术路线**：实时气象数据 → 结构化逐小时序列 → 可解释规则引擎 → 结论 + 依据 + 置信度 → 界面 / 问答；（可选）大模型只做意图分类与口语化改写。
和风天气
主预报→Open-Meteo
集合 / 置信度→logic.js
规则判定→结论 + 依据
数字只从这里出→llm.js
分类 / 润色 + 数字校验

- **模块划分**：weather.js 数据获取与归一化、logic.js 农事规则与问答、ensemble.js 集合预报评估、place.js 地名解析、app.js 渲染与交互、llm.js 大模型接入、pwa.js 安装与离线、content.js 界面文案、standards.js 属地作业标准、kb.js 本地知识库索引。
- **判定条件（v4.6 修正）**：除风速、气温、当日/前日雨量外，逐小时降水与**降雨概率**也参与判定（概率 ≥50% 或单小时降水 >0.1 mm 直接不排窗口）。此前只看雨量，会出现"降雨概率 70% 却给出可作业窗口"的错误，已修复并加回归测试。
- **本地知识库（离线）**：把已有真实数据建成可检索索引——13 份农技文件、24 个节气、6 条判定口径、167 个县级行政区，共 210 条；断网可用，问答命中时给出条目与出处，不调用大模型。
- **桌面专业视图**：逐时明细表（风速/风向/温湿/降水/概率/判定）+ 实况条（露点、气压、云量、日出日落），手机端自动隐藏，避免堆信息。
- **为什么不是「通用大模型套个界面」**：所有结论与数字由本地规则引擎产出；大模型仅在规则看不懂时做意图分类，以及把已确定的答案改得更顺口；改写若引入新数字会被拦截并回退。
- **异常处理**：接口超时 / 失败降级、集合预报缺失时改用主预报余量并明示口径、23 点后逐小时数据从次日开始时按日值补齐 7 天、地图 key 不可用时退回内置边界与离线底图。
- **可访问性**：纯静态站点 + Service Worker 离线壳；提供 PWA 安装与独立 WebView 安卓安装包，不依赖浏览器地址栏。

## 06. 选型对比

*和已有方案有什么不同*

| 方案 | 结论从哪来 | 能不能核对 | 边界是否诚实 |
| --- | --- | --- | --- |
| 通用大模型聊天窗口 | 模型自由生成 | 难，依据不可追 | 常会硬答 |
| 天气预报 App | 原始气象数据 | 能看数据，但没人翻译成农事动作 | 不涉及农艺判断 |
| **本作品** | **实时数据 + 可解释规则引擎** | **每个窗口给出风速 / 气温 / 雨量 / 阈值 / 成员支持率** | **划死知识范围，超范围明确拒答** |

> 差异不在「有没有用 AI」，而在「AI 被放在哪个位置」：这里它被放在不接触数字的环节。

## 07. AI 工具运用说明

*用了什么、人工做了什么*

- **用在哪里**：① 意图分类（规则读不懂的问题，让模型只输出类别）；② 口语化改写（把规则引擎已确定的答案说得更顺）；③ 超范围拒答的措辞；④ 开发阶段的代码与文档辅助。
- **不用在哪里**：不生成任何气象数字、不生成农艺阈值、不生成结论、不生成用户反馈与实验数据。
- **提示词设计**：分类提示词限定输出为固定枚举；改写提示词要求「不得新增数字、不得改变结论」，并附原文供校验；拒答提示词要求给出能力范围与建议渠道。
- **校验机制**：改写结果做数字一致性比对，出现新数字即拦截回退到规则原文，控制台留痕。
- **人工检查**：规则引擎、阈值口径、图表绘制与数据处理代码均由人工编写并逐项测试；AI 辅助生成的部分经过人工复核与端到端测试后才合入。
- **为什么选这个模型 / 平台**：对话增强选可替换的兼容接口（中转 / 直连 / 关闭三档），默认关闭，避免把作品可用性绑在某一家模型服务上；天气主源选和风天气是因为其逐小时与 7 天接口可直接支撑农事窗口计算，集合预报选 Open-Meteo 是因为可公开获取多模型成员用于置信度评估。

*怎么证明它能跑*

- **规则引擎单元测试**：`node web/test-logic.mjs`，覆盖窗口判定、雨阻、**降雨概率拦截**、灌溉、晾晒、城市字典、问答边界等，当前 242 项全部通过。
- **标准库离线测试**：`node web/test-standards.mjs`，校验文件编号/链接/取严方向与本地知识库条目，当前 164 项全部通过。
- **浏览器端到端测试**：`node web/e2e.mjs`，覆盖页面加载、七天卡片、图表、日切换、任务切换、地块增删改与持久化、问答、推荐追问、本地知识库检索、移动端布局等，当前 77 项通过。
- **构建自检**：`node scripts/build-site.mjs`，校验产物不含密钥、页面引用文件齐全、Service Worker 预缓存清单一致、微信验证文件随构建发布。
- **持续发布**：推送 main 分支触发 GitHub Actions 自动跑测试、构建、发布 Pages，线上地址可直接打开。

> **如实说明**：本地端到端测试有 2 项与高德地图相关，原因是本地 `localhost` 不在地图 key 的域名白名单内，线上域名访问正常；这是测试环境限制，不是功能缺失。本作品**尚未开展正式的用户试用与反馈收集**，因此不提供任何满意度、准确率提升或增产数据。

## 09. 运行与复现

*换台机器也能跑*

- **环境**：Node.js 20（仅用于本地服务 / 测试 / 构建）；浏览器用 Chrome / Edge 或安卓系统 WebView；无需数据库、无需后端服务器。
- **依赖**：源码零第三方运行时依赖；页面脚本均为原生 JS；地图、气象为公开 HTTP 接口；密钥类配置放在 `config.js`，本地私有配置不进仓库。
- **本地运行**：`node web/server.mjs` 后打开 `http://127.0.0.1:8931/`。
- **标准来源**：`web/standards.js` 收录 13 份国家 / 河北省 / 市级文件（含编号、发布单位、原文链接与查证日期）；离线测试 `node web/test-standards.mjs` 校验条目完整性与取严方向。
- **构建发布**：`node scripts/build-site.mjs` 生成 `site/`，整个目录可直接静态托管；仓库已配好 Pages 工作流。
- **手机安装**：站点支持添加到主屏；另提供独立 WebView 安卓安装包，不依赖浏览器地址栏。

## 10. 不足与改进

*哪里还不够*

- **长势判读尚未接入遥感**：当前图表为方法与形态示意，不代表任何实际苗情，本版本不输出长势结论；后续拟接入公开卫星影像计算 NDVI。
- **标准覆盖仍有缺口**：省级与部分市级文件已逐条核对，但县级文件多为转发省级，未逐县收录；张家口、廊坊等市的市级标准只拿到著录信息、未获全文，因此不按标题猜数值，统一回落到省级执行。
- **缺少真实用户试用**：计划面向种植户与农技专业同学开展试用，记录「结论是否被采纳、哪里判断错了」，再据此调整规则；目前没有这类数据，因此不写进效果结论。
- **知识范围偏窄**：病虫害、施肥、品种等高频问题仍不能回答，需要图像识别、土壤数据或有资质的知识库支撑。
- **气象不确定性**：集合预报只能提示分歧，不能消除它；临近时次的实况订正尚未接入。
- **对话上下文**：目前支持有限的追问与依据追问，尚不支持跨多轮的任务状态跟踪。

## 11. AI 伦理与合规声明

*红线相关，逐条说清*

- **AI 使用声明**：本作品在意图分类、答案口语化改写、拒答措辞与开发辅助环节使用 AI；规则引擎、阈值口径、数据处理、界面与测试代码由人工编写并复核。声明与实际使用一致。
- **数据与隐私**：不收集姓名、手机号、通讯录等个人信息；地块、阈值、AI 配置与纠错记录仅存于本机浏览器 localStorage；定位坐标只用于请求天气与地图选点，不上传本项目服务器。
- **素材与许可**：图标、背景、插画均为项目内程序化生成 / 手绘 SVG，无第三方图片、字体、音乐与人物形象；使用公开气象、地图与行政区划服务，遵循其公开接口的使用方式；未使用任何真实人物肖像或声音。
- **不编造**：不编造用户反馈、实验结果、产量或满意度数据；未接入的能力、未做的验证，在界面与说明书里均明确标注。
- **免责**：一切建议仅供参考。农事操作受土壤、品种、苗情、历史管理等影响，实际决策以当地农技部门意见与农药标签说明为准。

## 12. 三分钟演示提纲

*答辩怎么讲*

- **0:00–0:30 抛问题**：预报只说「多云 3 级风」，农户要决定几点下地打药——这个翻译谁来做？
- **0:30–1:10 看结论**：首页给出最近窗口（日期 + 几点到几点）、四宫格 KPI、适配度环与详细依据，点开集合预报支持率。
- **1:10–1:50 问依据**：切到「对话」，问「为什么这么判断」「这个结论准不准」，展示规则口径、数据来源与不确定性说明。
- **1:50–2:20 试边界**：问「该打什么药」，展示明确拒答与建议渠道；再点「记一条纠错」展示反馈闭环。
- **2:20–2:45 看依据**：「我的 → 作业标准」显示属地、每项限值的出处与原文摘录；问「按什么标准打药」可直接得到带文件编号的回答。
- **2:45–3:00 收尾**：翻到说明书第 8 / 6 / 10 节，指测试、选型对比、不足与改进；强调 AI 不碰数字、不编造数据。

## 13. 视觉与配色说明

*创意与艺术表现*
